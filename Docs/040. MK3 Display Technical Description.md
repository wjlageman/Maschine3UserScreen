# Technical Description: Maschine MK3 Display Interface

## Purpose

This manual describes how the Maschine MK3 display interface works within this project. The text is intended for developers who want to work with the display interface themselves or extend the existing application.

The description deliberately starts with the simple pixel demo. This route shows the minimum required to display graphics on the Maschine MK3 screens. The same foundation is then expanded into the Sciter/HTML/JS implementation.

## Important Nuance: 270 or 272 Pixels High?

Many descriptions of the Maschine MK3 displays refer to a resolution of 480 × 270 pixels. However, the current code in this project uses 480 × 272 pixels per display:

```cpp
static const int DISPLAY_WIDTH = 480;
static const int DISPLAY_HEIGHT = 272;
static constexpr int SCITER_WIDTH = 960;
static constexpr int SCITER_HEIGHT = 272;
```

The practical framebuffer used by this project is therefore 480 × 272 pixels per display and 960 × 272 pixels for both displays combined.

The difference from the commonly quoted 270 pixels may relate to visible active height, documentation rounding, or border pixels. For developers working on this project, the code is authoritative: draw and commit 480 × 272 pixels per display.

# 1. Where Is the Code?

## Maschine3UserScreen.h

Contains the main display-interface class and the most important display constants:

- DISPLAY_WIDTH
- DISPLAY_HEIGHT
- DISPLAY_BYTES
- COMBINED_WIDTH
- EP_OUT
- INTERFACE_NUMBER

Important values:

```cpp
static const int DISPLAY_WIDTH = 480;
static const int DISPLAY_HEIGHT = 272;
static const int BYTES_PER_PIXEL = 2;
static const int DISPLAY_BYTES = DISPLAY_WIDTH * DISPLAY_HEIGHT * BYTES_PER_PIXEL;
static const int COMBINED_WIDTH = DISPLAY_WIDTH * 2;

static const unsigned char EP_OUT = 0x04;
static const int INTERFACE_NUMBER = 5;
```

## Maschine3UserScreen.cpp

This is the core of the display interface. This file opens the USB interface, manages the framebuffers, and sends pixel data to the two displays.

- `open()` / `close()`: open and close the display interface
- `left_buffer()` / `right_buffer()`: access to the left and right framebuffers
- `commit_left()` / `commit_right()`: send a framebuffer to the corresponding display
- `send_frame_to_display()`: transmit header, command, framebuffer, and footer
- `write_bulk_exact()`: libusb bulk transfer with verification of the exact number of transmitted bytes
- `render_all()` and `render_dirty_side_after_draw()`: convert Sciter output into display data
- `request_display_update()`: maintain dirty state for the left and right displays

## GraphicHelpers.cpp / GraphicHelpers.h

Contains simple drawing functions for low-level RGB565 framebuffers. These helpers are primarily useful for test images and the simple pixel demo.

- `put_pixel_rgb565()`
- `fill_rect_rgb565()`
- `draw_border()`
- `draw_logo_block()`

## BannerDemo.cpp / BannerDemo.h

Contains the simple low-level demonstration. This is the best starting point for understanding direct display takeover without Sciter, HTML, or Javascript.

## Main.cpp

Contains detection of the correct Maschine MK3 USB interface and the driver-switching routes.

- `query_display_path()`: checks whether the display interface and endpoint are present
- `find_mk3_candidates()`: searches for Maschine MK3 candidates
- `qualify_mk3_candidate()`: tests whether the interface can be claimed
- `choose_preferred_mk3_candidate()`: selects the best candidate
- `run_driver_batch_elevated` / `run_driver_script_elevated`: launches the driver batches from `Maschine3Drivers`

## SciterSession.cpp / SciterSession.h

Connects the C++ display layer to Sciter. The Sciter window, HTML template, and render loop are started here. The position of the Sciter window is defined in `SciterSession.h`.

```cpp
static constexpr int SCITER_WINDOW_X = 4793;
static constexpr int SCITER_WINDOW_Y = 40;
static constexpr int SCITER_WIDTH = 960;
static constexpr int SCITER_HEIGHT = 272;
```

## SciterWindow.cpp / SciterWindow.h

Connects Sciter events to C++ functions. Particularly important is `request_display_update(x, width)`, through which Javascript reports which horizontal area must be processed again.

# 2. Windows Driver and Access to the Display Interface

The Maschine MK3 display interface is accessible only when Windows exposes this interface through WinUSB. WinUSB is a standard Microsoft Windows 10/11 driver. The project therefore does not use its own kernel driver.

In normal Maschine mode, Native Instruments uses its own driver. That driver gives NI exclusive control over the displays. As long as that route is active, this project cannot claim the displays.

Only the display interface is switched. The remaining USB interfaces of the Maschine MK3 remain available. Controller events are read through a different interface, and LED control uses yet another route.

## Installing and Restoring the Driver

Driver switching is performed through the batch files in the `Maschine3Drivers` folder. Use the `.cmd` files as the entry point, not the `.ps1` files directly.

```text
Maschine3Drivers\Set-MaschineMK3-UserMode.cmd
Maschine3Drivers\Reset-MaschineMK3-NIMode.cmd
```

`Set-MaschineMK3-UserMode.cmd` switches the display interface to WinUSB.

`Reset-MaschineMK3-NIMode.cmd` removes the WinUSB association and allows Windows to return to the Native Instruments route.

The `.cmd` files internally launch PowerShell with the correct parameters and working directory. Launching the `.ps1` files directly is not recommended because path, permission, and working-directory issues are more likely to occur.

Administrator privileges are required for driver installation and driver switching. Windows will therefore request confirmation.

If restoring NI mode is not immediately visible, power the Maschine MK3 off and on again. In some cases a Windows reboot is required. As a final recovery option, reinstall the NI software and driver.

# 3. Low-Level Pixel Demo Without Sciter

The simplest way to understand the display interface is the low-level demo in `BannerDemo.cpp`. This route draws directly into the two framebuffers and sends them to the displays.

There is no HTML, no Javascript, and no Sciter. The pipeline is:

```text
Maschine3UserScreen
→ left_buffer() / right_buffer()
→ draw RGB565 pixels
→ commit_left() / commit_right()
→ USB bulk transfer
→ Maschine MK3 displays
```

## RGB565 Explained

The displays use 16-bit colour data in RGB565 format. Each pixel therefore uses 2 bytes.

The 16 bits are divided as follows:

- 5 bits for red
- 6 bits for green
- 5 bits for blue

Green receives 6 bits because the human eye is more sensitive to differences in green. RGB565 is more compact than 24-bit RGB and is commonly used in embedded display interfaces.

Within this project, a pixel is written to the framebuffer as R5 G6 B5. The existing code writes the bytes in high-byte, low-byte order toward the display.

## Basic Route in Code

```cpp
Maschine3UserScreen display;

display.open(device);

auto& left = display.left_buffer();
auto& right = display.right_buffer();

// draw RGB565 pixels into left and right

display.commit_left();
display.commit_right();

display.close();
```

A complete display contains:

```text
480 * 272 * 2 = 261120 bytes
```

For both displays combined:

```text
522240 bytes
```

## Opening the USB Interface

The display interface is opened in:

```cpp
Maschine3UserScreen::open(libusb_device* device)
```

The steps are:

1. Close any existing handle.
2. Open the USB device using `libusb_open()`.
3. Attempt auto-detach with `libusb_set_auto_detach_kernel_driver(handle_, 1)`.
4. Claim the display interface using `libusb_claim_interface(handle_, INTERFACE_NUMBER)`.

The interface and endpoint are:

```cpp
INTERFACE_NUMBER = 5
EP_OUT = 0x04
```

If claiming the interface fails, the NI driver is usually still active, WinUSB is not active, or the Maschine MK3 must be reinitialised.

## Sending Data to the Display

Transmission takes place through `send_frame_to_display()`.

This function sends four bulk transfers in sequence:

1. header
2. command
3. framebuffer
4. footer

```cpp
write_bulk_exact(header, sizeof(header), 1000, ...)
write_bulk_exact(command, sizeof(command), 1000, ...)
write_bulk_exact(frame_data, frame_size, 3000, ...)
write_bulk_exact(footer, sizeof(footer), 1000, ...)
```

The actual transfer uses `libusb_bulk_transfer()` to `EP_OUT`.

`write_bulk_exact()` verifies that exactly the requested number of bytes has been transmitted. A partial transfer is treated as an error.

The header, command, and footer are part of the reverse-engineered display protocol. Do not modify these bytes without a specific reason.

# 4. Extension to Sciter

The Sciter implementation is built on top of the same low-level display layer. The difference is that the pixels are no longer drawn manually but originate from a Sciter window.

Sciter is a compact embedded HTML/CSS/JS engine for native Windows applications. The project uses the free Windows version with a fixed `sciter.dll` shipped with the application.

The Sciter route is:

```text
HTML/JS/Sciter window
→ Windows bitmap capture
→ BGRA buffer
→ split into left/right halves
→ conversion to RGB565
→ left/right framebuffer
→ USB bulk transfer
→ Maschine MK3 displays
```

## Physical Sciter Window Required

With the free Sciter DLL version, a physical window is used. The application therefore does not render completely headless.

The window does not have to be visible on a monitor, but it must exist as a Windows window so that its contents can be rendered and captured.

The Sciter window may be placed outside the visible monitor area. This is convenient because the user normally does not need to see the window.

## DPI Scaling

For pixel accuracy, the Sciter window must be located on a monitor or position without DPI scaling. Preferably use 100% scaling.

Do not place the window on a display using 125% or 150% scaling, as is common with many 4K monitors.

With DPI scaling, Windows may scale the client area differently than expected. As a result, the 960 × 272 pixel mapping is no longer exact and captures may become blurred or shifted.

## Changing the Position of the Sciter Window

The position of the Sciter window is configured in `SciterSession.h`:

```cpp
static constexpr int SCITER_WINDOW_X = 4793;
static constexpr int SCITER_WINDOW_Y = 40;
```

These values can be adjusted locally. Preferably choose a position on or next to a monitor using 100% DPI scaling. For debugging purposes it may be useful to temporarily place the window visibly on a normal monitor.

## Sciter Window Size

The Sciter layout uses a single combined display of:

```text
960 × 272 pixels
```

This is split into two halves:

```text
left:  x = 0..479
right: x = 480..959
```

Developers therefore design as if one wide display exists. The C++ layer then splits it into two physical displays.

# 5. Sciter Rendering to Maschine Displays

When the session starts, a complete render is performed through:

```cpp
display.render_all(frame)
```

This function forces a Sciter paint/update, captures the entire window, splits the image, and transmits both displays.

Afterwards, the application works with dirty updates. Javascript reports through:

```cpp
request_display_update(x, width)
```

which horizontal area must be processed again.

The C++ layer translates this into dirty flags per display half:

- update in left half: left display dirty
- update in right half: right display dirty
- update across the boundary at x = 480: both displays dirty

Important: the current C++ layer still ultimately transmits a complete left or right display. There is not yet a true partial USB update for a small rectangular region.

## WM_PAINT and Capture Timing

`SciterWindow` installs its own window procedure.

When `WM_PAINT` occurs, it marks that a draw update is required.

The render loop subsequently calls `pump_draw_update()`. At that point the relevant display half is captured and retransmitted.

Developers should therefore not attempt to read pixels immediately after a JS mutation. Use the existing update route through `request_display_update()`.

# 6. Notes for Developers

- The display height in the code is 272 pixels. Use that value for buffers and Sciter layouts.
- Many external sources mention 270 pixels. For this project, the framebuffer height in the code is authoritative.
- The Sciter layout is 960 × 272, not 480 × 272.
- The physical display boundary is at x = 480.
- Do not write RGB888 or BGRA directly into the display buffers. The display buffers expect RGB565.
- Use `BannerDemo.cpp` for low-level tests without Sciter.
- Use the Sciter route for real user interfaces with widgets, OSC, and controller integration.
- Start driver switching through the `.cmd` files or through the application menu, not directly through `.ps1` files.
- NI mode and user mode are exclusive; both cannot own the display interface simultaneously.
- If driver switching problems occur: disconnect/reconnect the Maschine MK3 and, if necessary, reboot Windows.

# 7. Summary

The display interface consists of a simple low-level foundation and a higher Sciter layer.

Low-level:

```text
RGB565 framebuffer → USB bulk transfer → Maschine displays
```

High-level:

```text
HTML/JS/Sciter → Windows capture → RGB565 framebuffer → USB bulk transfer
```

The most important code is located in:

- Maschine3UserScreen.cpp/h
- GraphicHelpers.cpp/h
- BannerDemo.cpp/h
- Main.cpp
- SciterSession.cpp/h
- SciterWindow.cpp/h

For developers, the most important point is that Sciter is only the rendering layer. The actual display interface remains the C++/WinUSB/libusb layer.
