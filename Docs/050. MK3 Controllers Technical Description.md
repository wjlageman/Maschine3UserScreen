# Technical Description: Maschine MK3 Controllers

## Purpose

This manual describes how the controller interface of the Native Instruments Maschine MK3 works within this project. The text is intended for developers who want to use the hardware events of the Maschine MK3 for their own instruments, controllers, or DAW integrations.

The focus is on:

- USB controller events
- the internal structure of the control frames
- routing to OSC
- controller event processing
- the separation between display, LED, and control interfaces

## 1. Architecture of the Controller Interface

The Maschine MK3 uses multiple USB interfaces. The displays, controllers, and LEDs do not use the same route.

- Display interface: separate USB bulk endpoint
- Controller events: separate interrupt/bulk input interface
- Controller event processing: separate output interface

As a result, controller events can be read while the Native Instruments software is still active.

Important difference compared to the display interface:

- The display interface is exclusive.
- The controller interface is not exclusive.
- The NI software still receives the controller events.
- This project passively reads the events.

## 2. Main Source Files

### MaschineUsbControls.cpp / .h

Low-level USB communication for controller events.

- opening the control interface
- read thread for incoming USB packets
- parsing raw control frames
- storing the current control state

### Maschine3ControlsRouter.cpp / .h

Processes decoded control events and converts them into:

- OSC messages
- Javascript callbacks
- event updates
- delta accumulation for encoders

### SciterWindow.cpp / .h

Connects controller events to Javascript.

- dispatch_control_to_js()
- js_get_delta_accu()
- js_reset_delta_accu()

### Udp_osc_transport.cpp / .h

Sends controller events as OSC messages via UDP.

## 3. Control USB Interface

The control events are read through a different USB interface than the display interface.

Important:

- The display interface uses INTERFACE_NUMBER = 5.
- The control interface uses its own USB interface.
- This interface remains active even when the NI software is running.

The control interface is opened through libusb:

```cpp
libusb_open()
libusb_claim_interface()
libusb_interrupt_transfer() or libusb_bulk_transfer()
```

## 4. Read Thread

The controller interface runs continuously in its own read thread.

This thread:

- waits for USB input packets
- decodes incoming bytes
- determines which controls have changed
- creates events
- places these events in a queue for OSC and Javascript

The read thread runs independently of display rendering. As a result, controller events remain responsive even when large display updates occur.

## 5. Structure of the USB Control Frame

The control interface uses HID input reports. The code reads these reports into a buffer of 64 bytes:

```text
CONTROLS_REPORT_SIZE = 64
CONTROLS_REPORT_OFFSET = 0x01
CONTROLS_DELTA_BYTES = 10
```

For normal control-state reports, the code processes report types 0x01 and 0x81 with a semantic length of 42 bytes. Report type 0x80 is a state-write echo and is ignored for controller events. Report type 0x02 contains pad records and is processed through a separate parser.

The button and touch states are read from report bytes 1 through 10. For each byte, bits 0 through 7 are compared with the previous state. Only changed bits are forwarded as events.

The name of a button or touch control comes from WidgetLookup.cpp. The bit_number in that table is translated as follows:

```cpp
report_byte = 1 + (bit_number / 8)
bit_in_byte = bit_number % 8
```

A bit value of 1 means pressed or touched. A bit value of 0 means released or not touched.

## 6. Event Decoding

The raw USB frames are translated into internal control events.

A typical event contains:

- control_name
- control_type
- value
- previous_value
- timestamp

Examples of control_types:

- button
- toggle
- encoder
- touch
- pad
- strip

## 7. Delta Accumulation

Encoders generate relative movements. For this reason, the application maintains delta accumulators.

Javascript can read these via:

```js
js_get_delta_accu(dial_index)
```

Afterwards, JS can reset the accumulator:

```js
js_reset_delta_accu(dial_index)
```

## 8. OSC Integration

All relevant controller events can be be sent as OSC messages.

Examples:

```text
/maschine3/button/play 1
/maschine3/button/play 0
/maschine3/dial/1 delta 2
/maschine3/pad/5 velocity 113
```

OSC is used because:

- it is faster and more flexible than MIDI for complex UI events
- Max/MSP and MaxForLive support OSC directly
- OSC can easily represent JSON-like data structures
- OSC works well for bidirectional controller interfaces

## 10. Cooperation with NI Software

The controller interface is less exclusive than the display interface.

As a result, controller events can be received simultaneously by:

- the NI software
- this project

This does not mean that all combinations are safe.

- state updates may conflict
- modes may overwrite each other
- the NI software may continue to process its own controller states

## 11. Timing and Performance

Controller events are small and fast. Most latency normally does not originate in USB, but in:

- Javascript processing
- OSC routing
- UI redraws
- DAW scripting

The controller read thread itself processes packets very quickly.

## 12. What Developers Should Not Do

- Do not place blocking code in the read thread.
- Do not perform extensive logging in high-frequency encoder loops.
- Do not make assumptions about fixed packet timing.
- Do not assume that all LEDs use RGB.
- Do not assume that pads use the same protocol structure as normal buttons.
- Do not tie display updates to every encoder tick without dirty filtering.
- Do not perform direct libusb writes outside the existing interfaces.

# Addendum: Exact Byte and Bit Layout of the Control Reports

This addendum describes the mapping used by the current decoder. The layout belongs to the control events and not to LED control. The LED interface uses different output packets and is described separately.

## Report Length and Report Types

The HID buffer has a fixed size of 64 bytes. For normal control-state reports, the code processes 42 semantic bytes. The remaining bytes are not used for event decoding.

```text
CONTROLS_REPORT_SIZE = 64
get_semantic_report_length(0x01) = 42
get_semantic_report_length(0x81) = 42
get_semantic_report_length(0x80) = 63
```

| Report Type | Semantic Length | Purpose |
|------------|------------------|---------|
| 0x01 | 42 bytes | Normal control state: buttons, touch bits, joystick step, dials, and touch strip. |
| 0x81 | 42 bytes | Normal control state using the same decoder route as 0x01. |
| 0x80 | 63 bytes | State-write echo; ignored for controller events. |
| 0x02 | HID report length | Pad records; sequence of 3-byte records starting at byte 1. |

## Joystick Step Encoder

| Event Name | Byte | Bits | Interpretation | Event Value |
|------------|------|------|----------------|------------|
| joy-step | 0x0B (11) | bits 0-3 | 4-bit counter | Delta via modulo 16; direction based on shortest distance. |

## Dials

The eight dials each use a 10-bit counter. For each dial, two bytes are read. The low byte contains bits 0-7. Only bits 0-1 of the high byte are used. The event value is the relative delta relative to the previous counter position, with wrap-around across 1024 steps.

| Event Name | Low Byte | High Byte | Used Bits | Interpretation |
|------------|----------|-----------|-----------|----------------|
| dial-1 | 0x0C (12) | 0x0D (13) | low byte + high bits 0-1 | 10-bit counter, delta with wrap-around |
| dial-2 | 0x0E (14) | 0x0F (15) | low byte + high bits 0-1 | 10-bit counter, delta with wrap-around |
| dial-3 | 0x10 (16) | 0x11 (17) | low byte + high bits 0-1 | 10-bit counter, delta with wrap-around |
| dial-4 | 0x12 (18) | 0x13 (19) | low byte + high bits 0-1 | 10-bit counter, delta with wrap-around |
| dial-5 | 0x14 (20) | 0x15 (21) | low byte + high bits 0-1 | 10-bit counter, delta with wrap-around |
| dial-6 | 0x16 (22) | 0x17 (23) | low byte + high bits 0-1 | 10-bit counter, delta with wrap-around |
| dial-7 | 0x18 (24) | 0x19 (25) | low byte + high bits 0-1 | 10-bit counter, delta with wrap-around |
| dial-8 | 0x1A (26) | 0x1B (27) | low byte + high bits 0-1 | 10-bit counter, delta with wrap-around |

## Touch Strip

The touch strip uses two 16-bit little-endian values. The counter at bytes 0x1C/0x1D provides strip.delta. The absolute raw value at bytes 0x1E/0x1F determines touch state, modwheel, wheel delta, and pitchbend.

| Event Name | Byte(s) | Source | Event Value |
|------------|---------|--------|------------|
| strip.delta | 0x1C-0x1D | uint16 little-endian counter | (curr_counter - prev_counter) / 16 |
| strip-touch | 0x1E-0x1F | uint16 little-endian raw | 1 if raw != 0, otherwise 0 |
| modwheel | 0x1E-0x1F | absolute value | raw - 1 while raw != 0 |
| wheel-delta | 0x1E-0x1F | absolute value | curr_abs - prev_abs; 0 at touch start/end |
| pitchbend | 0x1E-0x1F | absolute value minus touch-start base | curr_abs - g_strip_touch_base |

## Pad Records

Pads use report type 0x02 and are not processed through the normal bitfield decoder. The parser starts at byte 1 and reads records of three bytes until fn equals 0 or the report ends.

```text
record byte 0: pad
record byte 1: status
record byte 2: value_low

fn    = (status >> 4) & 0x0F
value = ((status & 0x0F) << 8) | value_low
```

| Record Function | Event Name | Meaning | Event Value |
|----------------|------------|---------|------------|
| fn = 1 | pad-N | velocity | value |
| fn = 3 | pad-N | release | 0 |
| fn = 4 | pad-N-pressure | pressure | value |
| fn = 4 | pressure | max pressure over records in report | max(value) |

## 13. Summary

The Maschine MK3 controller interface consists of a fast USB event layer that decodes controller events and makes them available to OSC, Javascript, and LED feedback.

```text
USB control frames
→ decode
→ internal events
→ OSC / JS
```

The most important components are:

- MaschineUsbControls.cpp/h
- Maschine3ControlsRouter.cpp/h
- SciterWindow.cpp/h
- Udp_osc_transport.cpp/h

Most important for developers:

- controller events are not exclusive
- display and control interfaces are separated
- encoders use relative deltas
- much button data uses bit fields
- OSC forms the primary route for external communication
