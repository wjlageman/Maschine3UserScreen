# Technical Description of the Javascript / Sciter Application

This manual describes the structure of the Javascript application that runs within the Sciter environment. The application forms the high-level user interface of the project and is responsible for converting `.htm` layouts into widgets, OSC routes, screen structures, and dynamic user interfaces.

## 1. General Architecture

The application avoids implicit modifications, hidden corrections, and automatic recovery mechanisms. Widget states are modified exclusively through explicit updates.

The rendering pipeline follows the model:

```text
layout → state → render
```

As a result, behaviour remains predictable and controllable.

The Javascript layer follows a strict state-based design. State forms the single source of truth for rendering and widget behaviour.

The Javascript application runs within an embedded Sciter browser environment. The C++ application starts Sciter, loads an `.htm` template, and connects the Javascript environment to the native display, control, and OSC interfaces.

The overall architecture is:

```text
Maschine3UserScreen.exe
→ Sciter
→ .htm template
→ ScreenCompiler
→ widget tree
→ OSC updates
→ render to Maschine MK3 displays
```

The Javascript code is responsible for:

- loading `.htm` screen layouts
- building the internal widget structure
- processing OSC messages
- binding widgets to controls
- managing widget states
- rendering widgets
- forwarding dirty regions to C++

## 2. The Role of Sciter

Sciter provides the embedded HTML/CSS/JS environment in which the application runs. The Javascript code does not use Sciter as a standard web browser, but as a compact UI runtime for specialised hardware interfaces.

Important characteristics of Sciter within this project:

- embedded HTML/CSS/JS environment
- fast startup
- small distribution size
- direct integration with native C++ code
- no full Chromium/Electron environment required
- pixel-accurate rendering for the Maschine MK3 displays

## 3. Widget Model

Internally, the user interface is built as a hierarchy of widgets and containers. The basic structure is visible in the class diagram.

Important base classes:

- Screen
- Region
- Box
- Widget
- PanelWidget
- MidiWidget
- ButtonWidget
- DialWidget
- MenuWidget
- ScrollWidget
- ToggleWidget
- RadioButtonWidget

The structure operates largely through inheritance. General properties such as position, size, labels, colours, and OSC bindings are managed in higher-level base classes.

## 5. ScreenCompiler

ScreenCompiler forms the core of the `.htm` parser. This component reads the `.htm` layout and converts it into an internal widget tree.

The compiler processes, among other things:

- screen tags
- region tags
- widget tags
- layout properties
- OSC routes
- control bindings
- widget parameters

During this process, widget objects are created through WidgetFactory.

## 6. WidgetFactory and WidgetDefAdapter

WidgetFactory is responsible for the actual creation of widget instances.

Based on:

- widget type
- tag name
- properties
- layout definition

the appropriate widget class is instantiated.

WidgetDefAdapter is responsible for converting raw `.htm` properties into internal widget definitions.

## 7. ScreenManager

ScreenManager manages the active screen structure.

Responsibilities include:

- loading templates
- building the widget tree
- management of `ui_state`
- widget initialisation
- integration with OSC updates

After a template has been loaded, the Screen instance is connected to the current `ui_state`.

## 8. OSC Processing

OSC messages are processed through OscMessage and the routing layers within the application.

OSC is used for:

- widget updates
- value updates
- colour changes
- state changes
- menu updates
- scroll positions
- toggle states

Widgets can be directly connected to OSC routes.

## 9. Widget Rendering

Widgets are rendered by Sciter within a single combined layout of 960 × 272 pixels.

After changes, the Javascript code marks dirty regions, which are then forwarded through the native C++ connection to the Maschine displays.

The Javascript application therefore does not render directly to USB or WinUSB. Rendering always takes place through Sciter and the native C++ display layer.

## 10. Controls and Widget Binding

Widgets can be bound to physical Maschine MK3 controls.

When no explicit `control="..."` property is present, the widget name is used as the default control name.

```html
<dial name="dial-1" />
```

becomes:

```text
control = dial-1
```

An explicit control property overrides this default binding:

```html
<dial name="cutoff" control="dial-1" />
```

This allows screen widgets to be flexibly connected to physical controls.

## 11. Layout Model

The screen layout is described in `.htm` files.

Important layout components:

- screen
- region
- box
- widget

The layout determines:

- allocation of screen space
- orientation
- grouping of widgets
- layout hierarchy
- initial widget structure

After compilation, the layout structure is fixed. During runtime, widget states and widget properties are the primary elements that change.

## 12. Important Design Choices

- strict separation between the native C++ layer and the Javascript UI layer
- OSC as the primary communication protocol
- widgets as the central abstraction
- layout compilation at startup
- dynamic widget updates through OSC
- pixel-accurate rendering through Sciter
- direct coupling between widgets and hardware controls

## 13. Summary

The Javascript application forms the high-level user interface of the project. The application compiles `.htm` layouts into widget structures, processes OSC messages, and renders the user interface through Sciter to the Maschine MK3 displays.

The most important components are:

- ScreenCompiler
- WidgetFactory
- WidgetDefAdapter
- ScreenManager
- OscMessage
- the widget hierarchy

The Javascript layer intentionally remains separated from the low-level USB and display code. As a result, the user interface and the hardware layer can be developed relatively independently from each other.
